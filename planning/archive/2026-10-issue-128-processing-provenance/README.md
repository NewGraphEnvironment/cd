## Outcome

Run provenance moved from four custom `cd:*` keys to the STAC processing extension v1.2.0 on both published metadata documents: `processing:version`, `processing:software` `{"cd": sha}`, `processing:datetime` (the `CD_RUN_TIME` string verbatim, since #126 matches it exactly) and a `processing-execution` link for a GitHub Actions run. One internal helper, `stac_provenance()`, feeds `cd_stac_item()` and the daily manifest's `manifest_entries()`, and one predicate, `has_processing_provenance()`, holds both documents to it: `manifest_problems()` and the new `catalog_vocab_problems()`, the latter in all four places a catalog is checked (STEP 1 on the live catalog, STEP 5, stage 3, `catalog_publish.R`). Two metadata-only republish paths were added so the COGs are never touched: `scripts/catalog_publish.R` (rebuilds `catalog.json` from the downloaded live COGs; refuses unless they are the live catalog's items over its span with every checksum unchanged; conditional upload; checkout must be on origin/main) and `daily_publish(sync = FALSE)` / `daily_publish.R --manifest-only`. What was learned: the plan review's blocker (pointing the repair hint at a script that refuses the hint's cases) and every code-check finding came from one mechanism — each publish entry point lists its own guards and operator text, and #128's metadata-only paths broke the #124 assumption that one run writes bytes and metadata together, so files' SHAs and "the catalog is always rebuilt by current code" had stood in for "the code writing the metadata is current". The loop ended by enumerating 6 entry points x 6 guards; the only unguarded cell (the pipelines' unconditional catalog `aws s3 cp`) predates #128. Schema facts are in [research/stac_extensions.md](../../../research/stac_extensions.md).
