# Code-check round 2: branch 124 (3c19b71...HEAD, at 79a9574)

## Findings

- **[severity: bug]** DESCRIPTION:51 (`terra` has no version floor), which breaks R/cd_cog_write.R:61-63 and R/cd_stac_catalog.R:112-117
  `cd_cog_write()` now runs `old <- terra::metags(x); old_name <- as.character(old$name)` on every call, including `tags = NULL`. `cd_stac_item()` reads `tags$value`, `tags$name` and `tags$domain`. Both depend on `metags()` returning a data.frame with a `domain` column, and terra only does that from **1.8-42** (2025-04-02, NEWS: "`metags` now supports raster metadata domains"). In terra 1.8-29, the CRAN archive source `R/tags.R` builds the dataset-level result as `out <- m[,2]; names(out) <- m[,1]`, which is a named character vector. `$` on that is an error: `"$ operator is invalid for atomic vectors"` (reproduced on the shape an untagged raster gives, `setNames(character(0), character(0))`).
  So on any terra older than 1.8-42, which DESCRIPTION still allows, every call of the exported `cd_cog_write()` fails, with or without tags, and so does `cd_stac_catalog()`. A user who never touches provenance is broken by this release. Nothing in this repo catches it: there is no R-CMD-check workflow, and pkgdown installs the current terra.
  Fix: `terra (>= 1.8-42)` in Imports. 1.8-50 is safer, because it also carries the `metags` matrix fix.

- **[severity: fragile]** scripts/_publish.R:12-21 (`head_object()`, no retry) as used by `etag_problems()` after the sync, with the remedy at scripts/_publish.R:243-252 (`daily_manifest_problems()`)
  The ETag check now sits between a sync that has already succeeded and the upload of the catalog or manifest. Each of its HEADs is a single `curl_fetch_memory()` with no retry, so one dropped connection (status 0) or one 5xx is reported as `"HTTP 0"` and stops the publish.
  - **Monthly.** The live COGs hold the new year and the catalog does not. The next run's STEP 1 refuses, and the operator has to apply `catalog_repair_hint()` by hand. That route works, but before #124 the only step after the sync was `aws s3 cp`, which retries internally. This change puts 59 unretried requests at the most expensive point in the pipeline. `read_live_years()`, a few hundred lines up, retries 3x for exactly this reason.
  - **Daily (worse).** CI's new year is on S3 but missing from `daily/manifest.json`. From then on every STEP D, the weekly heartbeat included, returns FALSE with "the live manifest ends in Y-1 but the cube is published through Y; repair from a full local cube: Rscript scripts/daily_publish.R". **That remedy refuses** in the case that produces this state: the local cube lacks year Y, because only the CI runner built it. Reproduced offline by sourcing `_lib.R` and `_publish.R` with the live manifest and `s3_tifs()` stubbed to "manifest 2001-2002, S3 2001-2003". `daily_publish()` stops with `the manifest would name 6 file(s), S3 would hold 9 after the sync: not in the manifest tmax_daily_2003.tif, ...`. CI cannot self-heal, so the run stays red until someone either rebuilds year Y locally (about 2 h of EDH) or works out that downloading the three live files into `data/backfill/daily/` and then running `daily_publish.R` repairs it. That route hashes the live bytes, the sync puts the same bytes back, and the ETags match. `aws s3 ls` and `s3api put-object` failures leave the same state, but the CLI retries those itself. The curl HEAD is the one step with no retry.
  Fix: retry `head_object()` on status 0 and >= 500, as `read_live_years()` does. Then either make the remedy text say "download `daily/<var>_daily_<Y>.tif` from S3 (or build year Y) into data/backfill/daily first", or have STEP D do that download itself when the manifest stops short of `newest`.

## Notes (not defects, or latent with no current instance)

- R/cd_cog_write.R:66-68. The "put back what is not provenance" claim, which the roxygen and the comment both make, is false when any kept tag value contains `=`. terra's `metags<-` (`parse_tags`) then switches to reading every element as `name=value` and silently drops the lot. Measured on terra 1.9.50: an input carrying `GRIB_IDS="CENTER=98(ECMWF) SUBCENTER=0"` and `units=degC` came out of `cd_cog_write(tags = ...)` with only `CD_*` and `AREA_OR_POINT`. There is no live instance. The real `swe_max_*` annual inputs carry 23 GRIB tags and none has `=` in its value; all 24 survived a real 1950-1951 write. It is worth one line in the docs, or passing the kept tags as a 3-column matrix rather than a named vector.
- Both pipelines run `stray_problems(cog_dir, ...)` before `unlink(file.path(cog_dir, "catalog.json"))` (pipeline_update_edh.R:959 vs 969, stage3:247 vs 257). A pre-#89 `catalog.json` left in `cog_dir` is therefore refused as a stray, and the unlink written for exactly that case never runs. This fails toward refusal (loud), and CI runners start empty, so it is cosmetic.
- scripts/_publish.R:93. `grepl("PreconditionFailed|412", out)` is unanchored (code-check-shell, "match error tokens anchored"). It only adds the "re-run to merge" hint, so a false match costs a misleading sentence, never a wrong decision.
- scripts/pipeline_stage3_edh.R:270. `stop("COGs synced, catalog.json NOT uploaded: ", problems, ...)` pastes two problem strings with no separator. Cosmetic.
- No step ever compares a live catalog's or manifest's checksums with the live objects, only the years. A stage3 republish whose catalog upload fails after the sync leaves correct years and wrong checksums, and no later run notices. stage3 is run by hand and that failure is a loud `stop()`, so this is a known limit, not a regression.

## Round-1 fixes: checked and sound

- **Hash, disk, S3 chain** (`checksum_problems()` after `etag_problems()`). For a file replaced before the sync, the post-sync checksum reddens. For one replaced between the sync and the ETag read, the ETag reddens. For one replaced between the two checks, the result is a false refusal only (safe). After the check, S3 holds the hashed bytes. Applied in all three publishers.
- **`daily_publish()` pgrep guard.** `system2("pgrep", c("-f", "<marker>"), stdout = TRUE)` returns nothing with status 1 when no match exists: macOS `sh -c` execs pgrep, so the guard does not match its own shell (measured). An unrelated process naming the script (an editor, `tail` on a log) causes a loud false refusal that names the pid. That direction is acceptable.
- **`s3_put_if()`.** The quoting of `'*'` and `shQuote(etag)` survives system2's shell join. `daily_manifest_live()` reads 403/404 as "absent". If that is wrong, the `--if-none-match '*'` write fails loudly rather than clobbering. Live HEADs return the bare ETag (`47a67dfd…`, `5701ffe3…-2`), and `manifest.json` currently returns 403 (none yet), as expected.
- **R `run_provenance()`.** A failed `git status` now gives `"unknown"`, which matches `_lib.py`. The fake-git test covers it.
- **`rewrite()` dirty-SHA refusal and the `main()` warning.** Both read `run_provenance()` once, at start, before any write.
- **Other checks.**
  - The S3 objects line up with the ETag code paths: all 59 monthly COGs are <= 5.84 MB (single-part, plain MD5), and the daily files are ~9 MB (2 parts at 8 MiB, in the candidate list).
  - `s3_tifs()` parses `aws s3 ls`, and its radix sort matches `manifest_merge()`'s.
  - `manifest_last_year()` and `newest` are both integer, so `identical()` holds.
  - The `.gitignore` entry covers the only untracked path a run creates. `.ruff_cache` carries its own `*` ignore, and `git status --porcelain` is clean at HEAD.
